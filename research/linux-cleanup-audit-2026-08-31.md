# Linux cleanup current-practice audit - 2026-08-31

## Result

The 21 August audits remain a sound baseline, and no reviewed APT, DNF, journal, Flatpak, Docker, or Podman command name has become invalid. This delta review found six material gaps: image-based DNF persistence, Docker Buildx target identity, container-store filesystem identity, logrotate configuration breadth, network pruning in the ordinary disk-cleanup path, and the availability of an observable interactive terminal. It also found a lower-severity authoring and evaluation gap.

The upstream Agent Skills specification has not materially changed since the previous audit: its official history shows no specification commit after 4 August 2026. The skill still passes the official validator. The findings below therefore arise from operational edge cases and current authoring guidance, not a new file-format requirement.

## Method and source hierarchy

This review compared the 21 August reports and the pre-change `skills/linux-cleanup/SKILL.md` at commit `307cb88` with current official documentation. Upstream project manuals and specifications were treated as authoritative for command semantics. OpenAI and Agent Skills documentation were used for skill authoring and evaluation practices. No third-party tutorial was used to support a finding.

Only deltas that alter execution safety, scope, persistence, or skill selection are included. Previously settled command semantics were not re-audited wholesale.

## Findings and recommended decisions

| Severity | Exact affected passage in the pre-change skill | Evidence | Minimal fix |
| --- | --- | --- | --- |
| **High** | DNF 4/5: "After approval, use either `dnf[5] clean packages` or `dnf[5] autoremove`." Scope establishment detected tools and versions but not an image-based host. | bootc says package managers normally operate at container-build time, recommends detecting read-only `/usr` or parsing `bootc status --format=json`, and says `bootc usroverlay` makes package changes ephemeral. Its filesystem model keeps `/usr` in the image lifecycle while `/etc` and `/var` may remain persistent. The overlay itself is transient and memory-backed. A DNF autoremove can therefore fail, reclaim no durable host space, or create split state across ephemeral `/usr` and persistent `/etc` or `/var`. [bootc package-manager integration](https://bootc.dev/bootc/package-managers.html), [bootc filesystem model](https://bootc.dev/bootc/filesystem.html), [`bootc usr-overlay`](https://bootc.dev/bootc/man/bootc-usr-overlay.8.html) | Detect read-only or image-managed `/usr`; when bootc is available, inspect its JSON status as data. Do not offer DNF/DNF5 autoremove as ordinary host cleanup unless durable package mutation is explicitly verified. On a default read-only or transient-overlay deployment, report it as unsupported for durable reclaim and direct package composition to the image build. Cache-only cleanup may remain eligible only after mapping its effective persistent store to the approved filesystem. |
| **High** | Audit: "Add `docker buildx du` when the selected builder matters." Execution later offered `docker builder prune`. | `docker buildx du` operates on the selected builder and accepts `--builder`; `docker buildx ls` exposes builders, nodes, and endpoints, including builders with remote SSH nodes. `docker buildx prune` also accepts `--builder`, whereas the generic `docker builder prune` reference provides no equivalent builder selector. Resolving the Docker daemon alone therefore does not prove the Buildx cache is local or that the cleanup matches the audited builder. [`docker buildx du`](https://docs.docker.com/reference/cli/docker/buildx/du/), [`docker buildx ls`](https://docs.docker.com/reference/cli/docker/buildx/ls/), [`docker buildx prune`](https://docs.docker.com/reference/cli/docker/buildx/prune/), [`docker builder prune`](https://docs.docker.com/reference/cli/docker/builder/prune/) | Record an explicit builder and every node endpoint before Buildx inventory. Stop if any node is remote unless that remote scope was requested. Pair `docker buildx du --builder NAME` with an approved `docker buildx prune --builder NAME`; do not substitute generic `docker builder prune` after a Buildx-specific audit. Recheck builder and nodes immediately before mutation. |
| **Medium** | "Inspect only installed subsystems that matter to the target"; Docker and Podman audit steps then resolve a daemon/connection but do not require its persistent storage roots to be on the approved filesystem. | Docker exposes its `Docker Root Dir` through `docker info`. Podman exposes store paths through `podman info`; containers/storage can put images in a separate `imagestore`, and Podman has an `--imagestore` override. A local daemon or connection can therefore consume a different filesystem, or more than one, without violating endpoint-locality checks. [`docker info`](https://docs.docker.com/reference/cli/docker/system/info/), [`podman info`](https://docs.podman.io/en/stable/markdown/podman-info.1.html), [containers/storage configuration](https://github.com/containers/storage/blob/main/docs/containers-storage.conf.5.md), [Podman global options](https://docs.podman.io/en/stable/markdown/podman.1.html) | Before inventory and proposal, map every relevant effective storage root to a mount identity. Record Docker Root Dir and Podman graph root, volume path, effective image store, and applicable CLI overrides. Include only storage on the approved filesystem; treat another filesystem as a separate scope requiring approval. |
| **Medium** | logrotate: "After approval, use `logrotate CONFIG`. Disclose configured pre- and post-rotate scripts and state changes." | The upstream manual defines command-line configuration files as the set of logs to handle, permits includes, and treats every file in a configuration-directory argument as configuration. A normal run can therefore rotate unrelated eligible entries and execute their scripts even when only one log motivated the proposal. Debug mode itself changes neither logs nor state. [upstream `logrotate(8)` source](https://github.com/logrotate/logrotate/blob/main/logrotate.8.in) | Follow the complete include closure shown by the preview. Run `logrotate CONFIG` only when every eligible entry, path, script, and state change is within the approved operation and filesystem. Otherwise stop after the audit; do not synthesize a narrower configuration or add `--force`. |
| **Medium** | Docker and Podman execution examples included `docker network prune` and `podman network prune` in the normal component-cleanup path. | Docker and Podman define network prune as removal of unused network configuration objects. Their disk-usage reports enumerate images, containers, volumes, and (for Docker) build cache, not networks. Network deletion therefore has no size-backed candidate or reclaim estimate under the skill's proposal contract. [`docker network prune`](https://docs.docker.com/reference/cli/docker/network/prune/), [`podman network prune`](https://docs.podman.io/en/stable/markdown/podman-network-prune.1.html), [`docker system df`](https://docs.docker.com/reference/cli/docker/system/df/), [`podman system df`](https://docs.podman.io/en/stable/markdown/podman-system-df.1.html) | Remove both network-prune commands from ordinary disk cleanup. Keep network removal behind a separate, explicit request, where the user is approving configuration-object deletion rather than measured storage reclamation. |
| **Medium** | Safety: "Keep prompts enabled and do not add ... automatic-confirmation ... options." The skill did not state what to do when the agent's shell cannot display or answer the prompt. | Official Agent Skills guidance warns that agent shells may be noninteractive and commands waiting for TTY input can hang. In this skill, adding noninteractive confirmation would defeat the explicit approval and candidate-review safeguards. This is an application of the official limitation to the skill's stricter safety model. [Agent Skills: avoid interactive prompts](https://agentskills.io/skill-creation/using-scripts#avoid-interactive-prompts) | Execute a prompt-bearing cleanup only in an interactive terminal where the prompt and candidate list are visible and the response is observable. If that capability is unavailable, stop at the proposal; do not add force or automatic-confirmation flags. |
| **Low** | Frontmatter: "Use for a full filesystem or a cleanup request." The repository also contains no committed evaluation cases. | OpenAI recommends a concise, tightly scoped description with important trigger words front-loaded because descriptions may be shortened. Agent Skills guidance recommends trigger/near-miss evaluation and comparison with a no-skill baseline. "cleanup request" is broader than Linux storage cleanup, while "full filesystem" is less likely than user language such as "disk is full" or "low on space." [OpenAI: Build skills](https://learn.chatgpt.com/docs/build-skills), [Agent Skills evaluation](https://agentskills.io/skill-creation/evaluating-skills), [description optimization](https://agentskills.io/skill-creation/optimizing-descriptions) | Narrow the description to Linux storage triggers, for example: "Use when a Linux disk is full or low on space, or the user asks to audit or reclaim storage." Add a small fresh-context evaluation set with positive triggers, adjacent negative cases, observable safety assertions, and a no-skill or previous-skill baseline. This is release evidence, not a runtime command correction. |

## Confirmed non-findings

- The prior GNU `du`, deleted-open-file, `os-release`, journald, package-cache recovery, DNF 5 audit-write, pacman privilege, Flatpak scope, Docker/Podman endpoint, prune granularity, and XDG cache decisions remain applicable.
- No new mandatory Agent Skills frontmatter field is missing. `compatibility`, `allowed-tools`, and `agents/openai.yaml` remain optional; adding them would not address an observed defect here.
- The skill remains comfortably below the Agent Skills recommendations of 500 lines and 5,000 body tokens, so splitting it would add navigation cost without a demonstrated benefit. [Agent Skills specification](https://agentskills.io/specification)

## Applied changes

- The description now uses concrete Linux storage triggers instead of the broad phrase "cleanup request."
- The scope phase detects image-managed hosts, maps package caches and container stores to filesystems, and resolves Buildx builders and node endpoints.
- DNF autoremove on bootc now requires evidence that the transaction is durable. A DNF 5 preview that may create user cache is a separately approved diagnostic operation, not part of the read-only audit.
- `logrotate` execution requires the complete include closure to remain in scope. Container network pruning no longer appears in the normal disk-reclaim path.
- Prompt-bearing commands require an observable interactive terminal. The skill now includes three behavioral evaluation cases and 16 positive or near-miss trigger queries under `evals/`; separate generator and grader artifacts are stored in `skills/linux-cleanup-workspace/iteration-1/`.

- The official validator was run from the current Agent Skills repository at commit `69ef37e9424c0a7ea9dd2293b559e43ec8176379` with `skills-ref validate skills/linux-cleanup`; result: `Valid skill`.
- The directory and frontmatter name match, the description is within the 1,024-character limit, and the only optional metadata field used, `license`, is allowed.
- Both evaluation files parse as JSON. In a controlled comparison, separate generators saw one prompt and one skill version but not the assertions; separate graders saw the responses and assertions but not the skills. The pre-change skill scored 0/13 and the candidate 11/13. The candidate passed all bootc and logrotate checks but compressed two Docker/Podman response requirements; those checks remain recorded as failures. These are single-run raw counts, not statistical estimates. The response files, evidence-bearing grades, benchmark, and run manifest are committed under `skills/linux-cleanup-workspace/iteration-1/`.
- Three independent description-only routing runs matched all 16 expected trigger and near-miss labels (48/48 classifications), including a balanced eight-query validation subset. The description was not changed after classifier output. Results and provenance are under `skills/linux-cleanup-workspace/trigger-eval/`.
- The official specification history showed no change after the 21 August audit window; the latest specification commit visible in the official repository was dated 4 August 2026. [official specification history](https://github.com/agentskills/agentskills/commits/main/docs/specification.mdx)
- No host cleanup command was executed during this audit.
